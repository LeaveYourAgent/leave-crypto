# leave-crypto

The cryptography inside the Leave apps for iPhone and Android, published so that what Leave says about it can be checked. An athlete's private strands, contracts and the reasons behind their Web's threads are encrypted on their own phone. The key that opens them all, the share, lives on the athlete's phones and is never sent anywhere unsealed. On iPhone it also syncs through iCloud Keychain when that is on. If the athlete makes a recovery code, a copy sealed with that code is stored on Leave's servers, and only the code opens it. On Android a copy can be carried to a new phone through Google's Block Store, only while the phone reports its backup as end-to-end encrypted. The server reads a record when a phone grants it that record's key for a session, at most 15 minutes, sealed to the server's own key. The server also makes some records itself (for example a strand saved from an AI app): it encrypts each with a fresh key and wraps that key to the account's public key, and the phone then wraps it to the share as well.

This repository is a copy of those files from the apps' private repository, taken at each release. It is not where the apps are developed, and pull requests are not merged here.

## What is here

| Folder | What it is | Built here? |
|---|---|---|
| `vectors/v1.json` | The shared test vectors: inputs and the exact bytes each operation must produce. Generated by Leave's server code; the server, the iPhone app and the Android app are all held to this one file. Every key in it is a test key made for the file. Its `grantV2` section (added 2026-10-30) is the next form of the server grant: a session ticket the server signs, and each record key sealed so that the server key version it was sealed to, the grant's expiry, its use, and each record's type and id cannot be changed. No released app or server uses it yet; it is published first so that both apps can be built and checked against it. The current form is tagged `vectors-grant-v2.1`; the earlier tag `vectors-grant-v2` is superseded (it did not bind the key version) and nothing was ever built on it. | — |
| `ios/Sources/LeaveCryptoCore/` | The iPhone's core: record encryption (AES-256-GCM), key wrapping, HPKE (RFC 9180) to a public key, the server grant (RSA-OAEP), the account key derived from the share, the device proof, and the recovery code (Argon2id via libsodium). Apple's CryptoKit and Security frameworks. | Yes, as the Swift package `LeaveCryptoKit` |
| `ios/Tests/` | The iPhone's tests against the vectors. | Yes |
| `ios/app-bridge/` | Where the iPhone app holds keys: the share in the Keychain (one slot per Leave account, synchronised through iCloud Keychain), data keys in memory, the phone's own Secure Enclave key. These use React Native and the app, so they are here to be read, not built. | No |
| `android/src/main/` | The Android core, the same operations in Kotlin on the JDK and Bouncy Castle. | Yes, as a plain JVM project |
| `android/src/test/` | The Android tests against the same vectors, and the Android side of the cross-check. | Yes |
| `android/app-bridge/` | Where the Android app holds keys: the share sealed under an Android Keystore key, data keys in memory, and the copy carried in Google's backup only while the phone reports that backup as end-to-end encrypted (`ShareCarry.kt`). To be read, not built. | No |
| `js/` | The app's JavaScript that calls the native modules: which records' keys are sealed to the server for a session, and how a key made by the server is re-wrapped to the share. To be read, not built. | No |
| `cross-check/` | One athlete on an iPhone and an Android phone with the server between them: each side seals with its own code and the others open it. The server's side is a test copy of the server's crypto on Node (`server-crypto.mjs`), not the server itself. | Yes |

## Running it

Needs: a Mac with Xcode (for `swift` and `swiftc`), JDK 17, and Node 20 or later.

```sh
# The iPhone's core against the vectors (fetches swift-sodium 0.9.1, the version the app ships)
cd ios && swift test

# The Android core against the same vectors
cd android && ./gradlew test --tests '*LeaveCryptoVectorsTest*'

# All three together: the iPhone's Swift, the Android Kotlin, and a test copy of the server's crypto on Node
./cross-check/cross-check.sh
```

## What this does and does not prove

- It proves that the code published here does what the vectors and the cross-check say, and that the iPhone, Android and server implementations agree byte for byte.
- It does not prove that a copy of the app from the App Store or Google Play was built from these files. Store builds cannot be reproduced byte for byte: Apple and Google re-sign them, and Apple's own processing changes the binary. What can be checked is this source against the protocol and the vectors.
- **Tags** mark the files an app release was built from, `ios-<build number>` and `android-<version code>`, with the SHA-256 of every file in `SHA256SUMS`. Tagging began with iPhone build 72 (1.2.0) and iPhone build 77 with Android version code 17 (1.3.0); the releases between 1.1.0 and those have no tag. The app repository's release check refuses a store build whose crypto files differ in code from the newest tag here. Comments are edited for publication (file paths, and the names of plans that are not public), and the tests are adapted to build here on their own, so that check compares the code with comments and blank lines left out. The first snapshot here (3a2a536) is the 1.1.0 source: iPhone build 69, Android version code 9.

## Not included

Some of the apps' native code that handles keys or encrypted files is not here, because it is mostly app plumbing rather than cryptography:

- Android: `LeaveDeviceKey` (the phone's own signing and agreement keys in Android Keystore; the iPhone's counterpart, `LeaveDeviceKey.swift`, is here), `ExportOpener` (opening the export archive), and the recovery code's bridge and screens.
- iPhone: the Zip and Files code (reading the export archive, encrypting and decrypting files on disk), and the recovery code's screens.
- Both: the upload code that sends already-encrypted files.

The recovery code's derivation itself (Argon2id, then AES-256-GCM) is in both cores here.
